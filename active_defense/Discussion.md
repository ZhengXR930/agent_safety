## Thread #1: 面向 agent 能力面风险的主动防御框架

**状态:Open**

### 0. 核心 idea

我们不去判断 agent 是否“有恶意”，也不在运行中逐步审查它的每个动作是否合规。我们的做法是：**在 agent 可见、可用的环境里预先放入一批“正常任务不该被真正用上”的标记，然后只观察这些标记有没有被真正用于后续动作。**

* 良性 agent 只会看到这些标记，不会把它们拿去继续做事；
* 被攻击带偏的 agent 一旦把标记真正用进后续动作，就留下了可观测痕迹。

这套方法成立的关键不在“标记本身”，而在**把标记放在攻击者绕不开的位置**——我们称之为**不可避免性**。整个框架只有两个基本落点：

* **PLANT**：把标记做成对象，混进攻击者必须处理的对象集合里，让它**排除不掉**。
* **WRAP**：把标记做成关口，放在危险动作的必经路径上，让它**绕不过去**。

### 1. 面向场景：agent 环境的能力面风险

我们面向的是**能读环境、能调用环境能力来完成任务的 agent**（如 Claude Code 这类 agent 平台）。这类 agent 的风险主要不来自模型“说错话”，而来自它**调用环境里的能力做了不该做的事**。我们把这一层统称为**能力面风险**。

环境里有两种基本元素：

* **能力单元（capability unit）**：agent 可以调用、用来产生实际效果的能力。
  **当前工作面向的能力单元是 `skill` 和 `MCP` 能力，而不是单个 tool。**
* **对象单元（object unit）**：agent 在完成任务时会读取、引用、传递的敏感对象，如 credential、datum、authorization 等。

> **为什么是 skill / MCP 能力，而不是单个 tool？**
> 防御边界本质是按**能力语义**定义的——我们要判断“这个单元本来被授权做什么、越界会做什么”，这是能力层的问题。单个 tool 太细：它往往只是某个更大能力的一个参数化入口，单看 tool 名字和 schema 很难稳定推断它代表的能力边界；而且同一能力常常分散在多个 tool 上，按 tool 建模会把一个完整能力切碎，导致边界难估、覆盖变形。所以方法层我们统一在“能力单元”这一粒度建模，`skill` 和 `MCP` 能力是当前最稳定的两类。实现上 Surveyor 仍可读取 tool schema 等更底层的材料，但那只是**发现能力单元的原料**，不是我们主张的建模粒度。

### 2. 能力面风险包含什么

能力面风险的共同形态是：**agent 把某个能力或某个对象，用在了它本来职责之外的后续动作上。** 具体可以分成几类：

1. **越权执行 / 提权**
   一个本应只读、只审查、只扫描的能力，被诱导去执行、安装、修改或放行。例如一个“扫描器”被带偏去“安装组件”，一个“审查者”被带偏去“签发放行”。

2. **数据外传**
   本应只被读取、汇总、上报的敏感数据，被带去发往外部出口（外部接口、外发消息、第三方端点）。

3. **凭证滥用**
   本应只在任务内部使用的 token / key / 配置，被拿去发起越权调用或访问越权资源。

4. **授权伪基础（authorization laundering）**
   agent 把一条“看起来已被批准”的依据，当成自己继续执行越权动作的理由。危害不在“说了一句话”，而在它**以此为据真的往下做了事**。

这几类风险的共同点，也正是我们检测的落点：**它们都需要 agent 把某个能力或对象“真正用上”，而不仅仅是看到。** 这就是本工作最重要的检测定义——**提交性使用**：喂进了一个会产生结果的后续动作（外传、调用、引用为依据、触发受控入口）。
只有提交性使用才算被标记捕获，把“无意路过”和“真的上钩”干净地分开。

### 3. 设计方案：
#### 3.1 设计原理：不可避免性
单纯埋一个假东西并不够。只要攻击者能把它认出来、或者直接绕开它，防御就失效。因此鲁棒性的真正来源只有一个：
**标记必须放在攻击者绕不开的位置。**
判断一个设计是否站得住，只看一个问题：**攻击者能否在完成目标的同时完全避开这个标记？** 

“绕不开”在数学上只有两种来源，这也是为什么**两个机制就足以覆盖能力面风险**——任何能力面攻击，要么动“对象”，要么走“动作”：
* 攻击要动**对象** → 用它**分不出真假**来锁死 → **PLANT**；
* 攻击要走**动作** → 用它**没有别的路**来锁死 → **WRAP**。

#### 3.2 PLANT：把标记做成“对象”
适用于攻击者必须从一组对象中挑选、读取、引用或外传某些对象的场景（对应 §2 的数据外传、凭证滥用、授权伪基础）。我们不去拦，而是往这组对象里混入一个**看起来像真、实则是假**的对象。只要攻击者把它一起外传、作为依据引用、或带进后续请求，就说明它被真正用上，检测成立。

PLANT 的关键不是“假”，而是**难以排除**：一眼假的诱饵会被跳过；与真实对象足够相像的诱饵，攻击者很难在不冒额外风险的情况下剔除。

典型例子：
* **假数据对象**：混进真实敏感记录，被一起导出/分享即触发；
* **假凭证**：混进真实 token / key / config，被拿去调用即触发；
* **假“已预授权”记录**：混进真实审批/例外单据，被引用为继续执行的依据即触发。

> **授权为什么归到 PLANT。** 若要求 agent“先来申请权限”，它在开放 shell 下完全可以不走这条路、直接把事做掉——这本质仍是 WRAP，会被绕开。反过来，环境里放一条看起来真实的“已批准”依据，越权 agent 为了给自己的动作找理由，更可能去引用它；一旦引用，假记录就已被真正用上，检测成立，**且与它最终走 skill、bash 还是别的路径无关**。

#### 3.3 WRAP：把标记做成“关口”

适用于危险动作存在一个**外部强制的执行入口**、想做这个动作就必须经过它的场景（对应 §2 的越权执行/提权中那些 agent 自己无法本地复刻的外部特权效果）。我们把标记放到这个入口前，agent 真调用受控入口即被记录。

WRAP 的关键不是“多一层包装”，而是**这层包装是否真的绕不过去**：如果 agent 能不走这个入口、自己复刻同样效果，WRAP 就不稳。

判断标准很简单：**这个效果，agent 在本地用 bash / curl / 脚本能不能自己做出来？** 做不出来、只能通过某个固定入口才能生效的，才适合 WRAP。典型例子：
* **打款 / 发起转账。** 钱实际从公司账户出去，这一步只有支付服务的 API 能完成，agent 本地写脚本造不出一笔真实交易。我们把标记设在这个支付接口前——agent 真去发起转账就被记录；它没有别的路能把钱划走。
* **对外发布 / 上线。** 把内容真正推到生产环境、发到公开渠道，这一步由发布平台独占，agent 本地复刻不了“已对外可见”这个效果。标记设在发布入口，触发即记录。
* **改动共享系统状态**（如改生产数据库、调权限、删云资源）。这些写操作只有对应的受控服务端能执行，agent 在自己的沙箱里改不动真实系统。标记设在该服务的调用入口。

这三个的共同点：**效果由一个 agent 管不到的外部系统强制兜底，想要这个效果就必须经过那个入口**，所以把标记放在入口前就绕不开。反过来，像“把文件发到外部邮箱”“把数据写进一个 webhook”这类 agent 自己用 curl 就能复刻的效果，就不满足这个条件——它有别的路，WRAP 不稳，应改用 PLANT（见 §3.4）。

#### 3.4 关键分流：`skill-as-shell`

这是覆盖能力面风险时最容易出错、也最需要单独说明的一点。

直觉上，既然每个 skill 都有职责边界，那似乎只要找出越界 skill、给它套上 WRAP 就够了。但这**只能做一半**，因为 skill 在两个层面上含义不同：

* **意图层：skill 是独立单元。** 它有名字、描述、授权范围和越界边界，可以拿来做边界分析。
* **执行层：很多 skill 只是 shell 的一份配方。** agent 读完 skill 说明后，完全可以不调用该 skill，而用 bash / Python / curl 自己复刻同样的效果。

所以对 skill 的边界分析**不能直接决定用 WRAP 还是 PLANT**，还要看它对应的效果在执行层是否可被复刻：

1. **效果可被 shell 复刻**（数据外传、本地状态修改、基于文档继续决策、引用“已授权”记录等）→ 不要把防御押在 skill 调用上 → 落到 **PLANT**，从最终结果检查标记是否被真正使用。
2. **效果由基座外部强制执行、agent 无法本地复刻**（如某个 MCP server 的专有能力）→ 可用 **WRAP**，因为此时能力调用就是必经路径。

因此 `skill-as-shell` **不是第三种机制**，而是 PLANT / WRAP 之间的**分流规则**：

* skill 提供边界语义；
* 效果可复刻 → PLANT；
* 基座强制中介 → WRAP。

一句话：**不是“见到能力单元就做 WRAP”，而是先分析它表示的越界意图，再按执行层是否可复刻来决定用 PLANT 还是 WRAP。**

### 4. Defense Harness 框架与各角色作用

代码上，框架分两段：一条统一的 **deploy-time 管线**（核心模块在 `code/defense/`），负责把标记设计好、校准好、部署进环境；外加一条**运行时轻量回路**，在部署后常驻，只做记录和增量自校正，不重跑整条管线。deploy-time 管线把“感知环境 → 设计标记 → 校准误报 → 选择 → 部署 → 评估”串成与具体环境解耦的流程：具体环境只通过 **binding** 提供差异，优化与编排逻辑共享。

**整体数据流：**

```
[ deploy-time 管线 ]
感知能力/对象单元  ->  为每个单元生成候选标记
   ->  在良性样本上校准误触率 (benign-fit)
   ->  选择要保留的标记 (PLANT 过可区分性认证 / WRAP 全覆盖)
   ->  伪装后部署进隔离环境
   ->  分别跑 attack 与 control  ->  汇总提交性使用指标

[ 运行时轻量回路 ]  (部署后常驻，不重跑上面的管线)
Logger 记录提交性使用痕迹
   ->  Updater 在线 benign-fit：发现某标记开始误触 -> 就地下线该标记
   ->  环境漂移时只补/换受影响的少数标记，不重做全量
```


#### 4.1 各角色的作用

角色分三类：**子代理**（真正起一个 Claude 进程去探索/设计/对抗，带语义判断）、**代码步骤**（确定性逻辑，无语义判断）、**运行时**（部署后轻量常驻）。

* **Surveyor（感知，子代理，`perceive.py`）**
  起一个 agent 进程读环境，把元素统一整理成 unit，不再只看 skill。对**能力单元**推导其授权范围与越界边界；对**对象单元**直接标记为可布置诱饵的位点。输出统一在 unit 层，后续流程不再关心“这是哪个 benchmark”。

* **Camoufleur（伪装，子代理）**
  为每个 unit 设计与环境风格一致的伪装：PLANT 的诱饵长得像真实同类，WRAP 的关口长得像环境里本就存在的入口。伪装质量直接决定“难以排除 / 不显眼”。

* **Distinguisher（可区分性认证，子代理）**
  专门服务 PLANT：在真实同类对象里尝试把诱饵挑出来。挑得出 → 诱饵不合格、需重做；挑不出 → 认证通过。它扮演“会主动排查可疑对象的对手”，把“难以排除”从口号变成可检验的门槛。

* **Calibrator（校准，代码 + 良性回放）**
  在 **held-out 的良性样本**上部署候选标记，统计每类角色的误触率 δ。良性会误触的标记直接弃用，保证近零误报；因为是 held-out，评估集上的误报不是 in-sample（无泄漏）。

* **Optimizer（选择，代码）**
  当前不是复杂的预算优化，而是两条直接规则：**保留所有良性不误触的标记**；**对 PLANT 额外要求通过可区分性认证**。即贡献点不在优化算法，而在“位点找得对、分流分得对、伪装做得真、误报校得准”。

* **Deployer（部署，代码）**
  把选中的标记按伪装方案注入隔离工作环境，准备 attack / control 两类 episode。

* **Harness（执行骨架，代码，`harness.py`）**
  统一驱动上述流程并并行跑 case。它只要求 binding 提供五件事：如何感知 unit、如何生成候选标记、如何在隔离环境部署、如何跑 attack / control、如何从结果判定哪些单元被真正使用。具体环境的差异全部封进 binding，编排与选择逻辑共享。

* **Orchestrator（编排，代码，`orchestrator.py`）**
  把 Surveyor / Camoufleur / Distinguisher 这三个子代理按环境组织起来：每个环境只开一次会话、把结果缓存成可复用的 plan，而不是每个 case 重新手写。重点不在“多 agent”，而在把感知、伪装、可区分性检验固化进同一个可复用的计划阶段。

* **Logger / Updater（运行时）**
  Logger 记录提交性使用的痕迹；Updater 做在线 benign-fit（误报自校正）与环境漂移适配。

#### 4.2 我们到底在量什么

harness 最终关心两类信号：

* **攻击侧**：攻击成功时，有多少被标记的单元被真正用上（提交性使用）；
* **良性侧**：正常任务下标记会不会被误触。

强调“提交性使用”而非“看到”的原因始终一致：看到不足以说明被带偏，**真正用上**才是攻击已经押注这个标记的证据。

### 5. 适用范围与不主张的部分

**我们主张：**

* **开放 shell 环境**下主力机制是 **PLANT**——检测读最终结果，不依赖 agent 是否老实运行我们的脚本或走预设能力路径；
* **基座外部强制中介**的环境下，**WRAP** 可给出强主张（如 MCP server 端或受控 function-call 接口，agent 无法绕开入口、也无法本地复刻效果）；
* **authorization / approval** 这类“依据型”对象，在开放 shell 下优先归入 **PLANT**。

**我们不主张：**

* 不主张“所有 skill 都适合做 WRAP”——skill 可能只是 shell 配方，而非不可绕过的入口；
* 不主张“多加一个审批/permission 步骤就能解决问题”——若非基座外强制，开放 shell 下仍可绕过；
* 不主张“贡献点在优化算法”——旧的预算型优化叙事已退场，当前重点是框架设计、正确分流、伪装与校准；
* 不主张“面向单个 tool”——我们面向的是能力单元（skill / MCP），tool 仅作发现原料。

### 6. 与现有方案的分界

* **对比 AgentShield**：它依赖固定 trap。若攻击者只用合法工具、合法对象和局部决策完成危害、完全不碰固定 trap，检测就失效。我们的区别是：标记跟着环境位点和攻击意图走，并要求放在绕不开的位置。
* **对比 IFC 类方法（Fides / AgentArmor）**：它们在运行时追踪信息流或标签传播；我们不依赖在线标签、不在运行中逐步判定合法性，而是先制造位点、再观察最终是否被真正使用。

### 7. 当前开口

当前仍需做实的关键点不是“有没有诱饵能抓到”，而是：

**当攻击者会主动识别并排除可疑对象时，可区分性认证（Distinguisher 那一步）到底是不是必要条件。**

即下一步要补的是“排除型对手”下的验证，而不是继续堆更多例子。
